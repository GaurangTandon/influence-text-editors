What is actually being tested

An iframe is a second realm. Same origin, so every object is reachable by ordinary JavaScript — there is no permission to ask for and nothing to negotiate. What changes is that InputEvent, DataTransfer, StaticRange and ClipboardEvent are now different objects, one set per realm. Two questions decide everything else:

  1. Does an own property that one realm defines on an event — the shadowed getTargetRanges(), the shadowed clipboardData — reach the other realm's listeners?
  2. Does a DataTransfer built in one realm satisfy another realm's instanceof DataTransfer? CKEditor 5 checks, and throws when the answer is no.

The five steps of the recipe, and which of them survive the crossing, are measured in the Probes section at the bottom. The matrix above the probes is the consequence; the probes are the cause.

The workarounds these questions are about exist to dodge two engine bugs, tracked upstream — the per-editor evidence is on this page:

  • WebKit bug 170416 — Support InputEventInit.{… targetRanges} (open PR 19346): without it, WebKit has no spec'd target-range route, so the own-property shadow is load-bearing — and this page measures that the shadow does cross a same-origin realm.
  • Mozilla bug 2027025 — ClipboardEvent constructor does not set clipboardData: without it, Firefox's paste needs the real-DataTransfer shadow, which this page measures as crossing the realm too.
