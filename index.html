Strategies for influencing text editors

One piece of JS modifies the contents of an editor it is not attached to, by means of one of several strategies:

  • beforeinput as insertReplacementText
  • beforeinput as insertText
  • beforeinput as deleteContentBackward
  • synthetic paste
  • faked Backspace keypress
  • execCommand

Five real editors, mounted stock — no hooks, no listeners, nothing customised — react to them very differently. Switch between the editors and press the same seven buttons.

What every strategy has in common

Steps 1, 2 and 5 are shared by every strategy. Steps 3 and 4 are where beforeinput differs from the rest.

  1. Build a Range over the text to be replaced. Mapping character offsets onto DOM points with a TreeWalker over text nodes is the only portable way: inline formatting splits one sentence across many text nodes, so child indices are useless.
  2. Put the live DOM selection on that range, then fire selectionchange at the document, the element and the window. Rich editors keep their own selection model and only re-sync when they observe one. Skipping this is why the paste rows below can land at the caret instead.
  3. Dispatch the strategy, then confirm the edit landed where it was aimed by re-reading the text. Never treat "not preventDefaulted" as success — a synthetic event has no default action, and CKEditor 5 even returns true from execCommand while changing nothing.

What makes the beforeinput event different

getTargetRanges() is a method on InputEvent.prototype, not a member of the constructor's init dict. A beforeinput you build yourself therefore always reports an empty target range. Filling it in takes one Object.defineProperty and a real StaticRange:

  1. Construct new InputEvent("beforeinput", { inputType: "insertReplacementText", data, dataTransfer }). Formatting cannot travel in data — it is a plain string — so it goes in the dataTransfer's text/html flavour.
  2. Attach the target range, because the constructor cannot. 
const staticRange = new StaticRange({
  startContainer: range.startContainer, startOffset: range.startOffset,
  endContainer:   range.endContainer,   endOffset:   range.endOffset,
});
Object.defineProperty(event, "getTargetRanges", {
  value: () => [staticRange], configurable: true,
});

A real StaticRange rather than a plain object literal, because consumers read .collapsed off it — and because a target range is by definition read-only: the editor may read it, never mutate it. A ClipboardEvent has no target-range concept at all, which is why the paste rows below can only act on the current selection.
